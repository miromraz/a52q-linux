# A52q (SM7125) SSC / ADSP sensor rails — evidence

Date: 2026-10-02
Branch: `a52q/ssc-rails` (off `a52q/integ`), worktree `~/src/wt-ssc`

## Problem

On mainline, the ADSP SEE sensor framework loads the vendor registry, then ~5 s
later dies with a `sns_thread_mana` / `UTMR_CLNT_1` watchdog fatal
(`EF:sensor_process:...`), hard-resetting the phone. With empty sensor configs
there is no crash (nothing probed). Hypothesis: a sensor supply the AP must keep
up is not enabled in the mainline DT, so SEE blocks on the sensor bus until the
thread-manager watchdog fires.

## Sensors (vendor registry) → bus / address / IRQ / rail

Source configs: `~/linux-a52q/sensors/root/sensors/config/`
(bus_type: 0 = I2C, 3 = SPI; bus_instance = SSC QUP SE index; IRQ num is an
SSC/LPI GPIO on the ADSP, not an AP TLMM pin.)

| Sensor | Role | Bus | Addr/CS | IRQ (SSC GPIO) | Rail(s) in config | Config file |
|-|-|-|-|-|-|-|
| LSM6DSO | accel/gyro | SPI SE1 | CS 107, DRI | SSC gpio 4 | `sensor_vddio` | `atoll_qrd_lsm6dso_0.json` |
| AK0991x | magnetometer | I2C SE4 | 0x0C | polled | `sensor_vddio` | `atoll_qrd_ak991x_0.json` |
| STK31610 | ambient light | I2C SE5 | 0x48 | polled | `dummy_vdd` (unmanaged) | `atoll_qrd_stk31610_0.json` |

Field evidence:
- `atoll_qrd_lsm6dso_0.json`: `bus_type=3`, `bus_instance=1`, `slave_config=107`,
  `dri_irq_num=4`, `num_rail=1`, `vddio_rail=/pmic/client/sensor_vddio`.
- `atoll_qrd_ak991x_0.json` (`ak0991x_0_platform/.config`): `bus_type=0`,
  `bus_instance=4`, `slave_config=12` (0x0C), `num_rail=1`,
  `vddio_rail=/pmic/client/sensor_vddio`.
- `atoll_qrd_stk31610_0.json` (`stk31610_0_platform/.config`): `bus_type=0`,
  `bus_instance=5`, `slave_config=72` (0x48), `num_rail=2`,
  `vdd_rail=/pmic/client/dummy_vdd`, `vddio_rail=/pmic/client/dummy_vdd`.

Two of three SSC sensors (LSM6DSO, AK0991x) require the SEE PMIC client
`sensor_vddio`. `/pmic/client/...` names are resolved on the ADSP side via RPMh;
there is no AP-side sensor driver to turn the rail on, so SEE assumes it is
already up. STK31610 declares `dummy_vdd` (SEE does not manage it) and is a
single-supply 1.8 V part, so it rides the same always-on IO rail.

## `sensor_vddio` → physical LDO (downstream DT)

Samsung downstream (`~/src/android_kernel_samsung_sm7125`,
`arch/arm64/boot/dts/samsung/atoll-sec-a52q-r00.dtsi` lines 29–48):

```
//Sensor Vdd
rpmh-regulator-ldoc8 {
    ...
    L8C:
    pm6150l_l8: regulator-pm6150l-l8 {
        regulator-name = "pm6150l_l8";
        regulator-min-microvolt = <1800000>;
        regulator-max-microvolt = <1800000>;
        regulator-always-on;          // <-- kept on for the sensors
        ...
    };
};
```

So the SSC sensor VDDIO is **pm6150l LDO8 @ 1.8 V**, explicitly labeled
`//Sensor Vdd` and marked `regulator-always-on` downstream.
(Downstream also keeps `//Grip Sensor Vdd` = pm6150 L5 @ 3.3 V always-on, lines
52–58 — that is the AP-I2C grip sensor, **not** an SSC sensor, and is not in the
SEE registry, so it is out of scope here.)

Mainline equivalent: `vreg_l8c_1p8` (pm6150l ldo8), defined in
`sm7125-samsung-common.dtsi:346`, fixed 1.8 V, currently **not** always-on and
with **no** other consumer in the sm7125-samsung DTs — i.e. in mainline it can
be powered off, which matches the observed SEE bus hang / watchdog reset.

The SSC IRQ lines (LSM6DSO DRI = SSC gpio 4) live on the ADSP's own LPI/SSC GPIO
controller, not the AP TLMM, so no AP-side pinctrl change is required or
possible. Only the supply is an AP responsibility.

## Change

`arch/arm64/boot/dts/qcom/sm7125-samsung-a52q.dts`: mark `vreg_l8c_1p8`
`regulator-always-on` with a comment naming the three SSC sensors and the
downstream source. Scoped to the a52q board file (not the shared
`sm7125-samsung-common.dtsi`, which a72q also includes) to match downstream's
board-level placement and keep blast radius minimal.

Only `sensor_vddio` (= vreg_l8c_1p8) is enabled. No other rail is touched:
downstream confirms exactly this one 1.8 V LDO as the always-on SSC sensor
supply, and enabling rails that are not confirmed-correct can damage hardware.
