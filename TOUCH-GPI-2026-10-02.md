# Touch I2C GPI timeouts on a52q (SM7125 / sc7180), mainline 7.3 — root cause

Date: 2026-10-02
Kernel: a52q/integ = v7.3-rc5-129-g706d11953a6b
Bus: QUP1 SE1 = i2c7 @ a84000, touch FTS5CU56A @0x49 (stmfts_fts5cu56a v2)

## Symptom
At ~338 s uptime, under touch traffic:
```
geni_i2c a84000.i2c: geni_i2c_gpi_xfer:I2C timeout
geni_i2c a84000.i2c: GPI transfer failed: -110
gpi a00000.dma-controller: cmd: CH STOP completion timeout:0 / ret:-5
gpi a00000.dma-controller: cmd: CH STOP completion timeout:1 / ret:-5
```

## Root cause (confirmed)
Upstream **regression in `drivers/dma/qcom/gpi.c`**, exposed on every geni-i2c
GPI read. It is **not** a DT / SE-number / compatible problem and **not** the
touch driver.

In GPI mode an I2C *read* is a two-channel transaction:
- TX channel gets CONFIG0 + a **GO** TRE (the i2c driver calls `geni_i2c_gpi()`
  with `op == I2C_WRITE` and sets `peripheral->multi_msg = true`),
- RX channel gets the DMA TRE that receives the data.

`gpi_create_i2c_tre()` builds the GO TRE for the `multi_msg` case with
`TRE_FLAGS_LINK` but **without `TRE_FLAGS_IEOB`** (Interrupt on End of Block).
With no interrupt flag on *any* TX TRE, GSI never raises a completion event on
the TX channel, so the TX ring read pointer never advances and TX descriptors
are **never retired**. The per-transfer completion the i2c driver waits on is
fired by the RX callback, so each individual read still returns — the TX leak
is silent. Under sustained high-frequency traffic (touch polled at 120–240 Hz)
the fixed-size TX ring fills after a few hundred reads (~338 s of touch use),
the next GO TRE can no longer be queued, the transfer times out (-110), and the
teardown then fails `CH STOP` on both channels because the channel is wedged.
The `CH STOP` errors are secondary, not the trigger.

Note the sibling `gpi_create_spi_tre()` already sets `TRE_FLAGS_IEOB` on its
linked GO TRE (SPI_RX path) — I2C simply never got the equivalent.

### Why the 6.14 fork (obs/sm7125) worked for weeks
Same board, same DT, same GPI mode, same SE. The fork predates the geni-i2c
multi-descriptor/BEI series. The exposure was widened by
`656147fb1d4c ("i2c: qcom-geni: Avoid extra TX DMA TRE for single read message
in GPI mode")`, which made single reads take the `multi_msg` GO-TRE path — the
path missing IEOB. That commit is **not** in the fork; it is in 7.3-rc5. Hence
the fork never hit it and integ does on every touch read.

## Answers to the three questions
1. **compatible / SE / channel numbers are correct.** integ's
   `sc7180.dtsi` GPI is byte-identical to the working fork:
   `gpi_dma1@a00000` = `"qcom,sm6350-gpi-dma"` (ee offset 0x10000 is right for
   sc7180 — same as the fork that ran for weeks; an sdm845-style ee-offset-0
   compatible would be wrong). `i2c7@a84000` uses
   `dmas = <&gpi_dma1 0 1 QCOM_GPI_I2C>, <&gpi_dma1 1 1 QCOM_GPI_I2C>` and clock
   `GCC_QUPV3_WRAP1_S1_CLK`. SE index **1** on QUP1 is correct for i2c7
   (a80000=S0=i2c6, a84000=S1=i2c7). **No DT change needed.**
2. **Known upstream fix exists — carried.** "dmaengine: qcom: gpi: Set IEOB on
   linked I2C GO TRE to retire TX descriptor" (Vsevolod Nevorotov, Reviewed-by
   Dmitry Baryshkov; linux-arm-msm, Sep 2026; `Fixes: 656147fb1d4c`). Applied on
   branch `a52q/gpi-fix`. (patchwork + lore are Anubis/403 bot-walled here;
   diff recovered from the ratatoskr.run mailing-list mirror.)
3. **Runtime PM / touch read pattern are not the cause.** The touch driver only
   issues `i2c_smbus_read_i2c_block_data` (num=2: write-cmd + read) and
   `i2c_master_send` (num=1 write); it never hits the ≥2-write multi-descriptor
   BEI path. The 338 s delay is TX-ring exhaustion from the IEOB leak, not an
   autosuspend/resume race or large-FIFO read.

## Fix
`drivers/dma/qcom/gpi.c`, 2 hunks (+11 / −2):
- set `TRE_FLAGS_IEOB` on the GO TRE when `i2c->multi_msg` (so GSI raises the
  TX EOB event), and
- in `gpi_process_xfer_compl_event()`, on `MSM_GPI_TCE_EOB` for a linked
  `QCOM_GPI_I2C` desc, retire the TX descriptor (`dma_cookie_complete` +
  free) without calling the client callback — RX completion still signals the
  final result.
